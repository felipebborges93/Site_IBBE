<objective>
Implementar a infraestrutura de segurança, sanitização de entrada, anonimização e persistência da Server Action de pedidos de oração conectada ao Supabase via cliente `@supabase/ssr` anônimo.

Purpose: Garantir ingestão íntegra de pedidos de oração, prevenindo spam via honeypot, protegendo contra abusos via rate limiting LGPD-compliant por hash de IP, prevenindo XSS via sanitização estrita de HTML e garantindo o sigilo de pedidos anônimos.
Output: Módulos `lib/rate-limit.ts`, `lib/sanitize.ts`, schema refinado `lib/validations/prayer.ts`, Server Action `app/actions/prayer.ts` e suíte de testes `tests/e2e/prayer-security.spec.ts`.
</objective>

<threat_model>
| Threat | ASVS Category | Severity | Mitigation |
|---|---|---|---|
| Spoofing de Identidade | V2: Authentication / Identity | Medium | IP hashing com salt estático em memória impede rastreamento de IPs reais e previne spoofing de cabeçalhos |
| Injeção / XSS via HTML | V5: Validation & Sanitization | High | Sanitização estrita em `lib/sanitize.ts` remove tags HTML e escapa caracteres perigosos antes da validação Zod e persistência |
| Violação de Privacidade LGPD | V4: Access Control & Privacy | High | Nenhum IP bruto é persistido em banco de dados; pedidos anônimos forçam campo `name` a `null` no backend (D-04) |
| Abuso por Bots / Spam | V11: Business Logic / Abuse | High | Campo honeypot invisível (D-01) aborta silenciosamente simulando sucesso; rate limit restringe a 3 requisições/hora por hash de IP (D-02) |
| Escalada de Privilégios no Banco | V1: Architecture & RLS | High | Inserção utiliza cliente Supabase SSR anônimo (`anon`), forçando políticas RLS de `status='pending'` e `displayed=false` |
</threat_model>

<action>
1. Criar `lib/rate-limit.ts` exportando a interface `RateLimitRecord` (`count: number`, `lastReset: number`), a função `hashIp(ip: string, salt?: string): string` usando `crypto.createHash('sha256').update(ip + ':' + salt).digest('hex')` (com fallback do salt para `process.env.RATE_LIMIT_SALT || 'ibbe-prayer-salt'`), e a função `checkRateLimit(ipHash: string): { allowed: boolean; remaining: number }` utilizando `Map<string, RateLimitRecord>` em memória com janela de 1 hora (`60 * 60 * 1000` ms) e limite de 3 requisições por hora (conforme D-02).
2. Criar `lib/sanitize.ts` exportando a função `sanitizeHtml(input: string): string` que remove tags completas `<[^>]*>` e escapa caracteres especiais `<`, `>`, `'`, `"`, `&` garantindo texto puro sem exceção (conforme D-03).
3. Atualizar `app/actions/prayer.ts` para exportar a interface `PrayerActionState` com campos `success: boolean`, `message: string`, `errors?: Record<string, string[]>`.
4. Na função `submitPrayerRequest(prevState: PrayerActionState | null, formData: FormData)`:
   - Extrair `rawData` de `formData.entries()`.
   - Verificar honeypot (D-01): se `rawData.honeypot` for string não vazia após trim, emitir `console.warn` e retornar silenciosamente `{ success: true, message: 'Pedido enviado com sucesso!' }`.
   - Extrair IP a partir de `headers()` do Next.js via cabeçalho `x-forwarded-for` (primeiro item separado por vírgula) com fallback para `'127.0.0.1'`.
   - Obter hash via `hashIp(ip)` e verificar `checkRateLimit(ipHashed)`. Se `!allowed`, retornar `{ success: false, message: 'Limite de pedidos atingido (máximo de 3 pedidos por hora). Por favor, tente novamente mais tarde.' }` (conforme D-02 e PRAY-03).
   - Sanitizar campos `name` e `request` via `sanitizeHtml` (D-03, PRAY-02).
   - Validar com `prayerFormSchema.safeParse`. Se falhar, retornar `{ success: false, message: 'Verifique os campos do formulário.', errors: validated.error.flatten().fieldErrors }`.
   - Redação de anônimos (D-04, PRAY-04): definir `finalName = validated.data.is_anonymous ? null : validated.data.name`.
   - Obter cliente Supabase via `await createClient()` de `@/utils/supabase/server` e persistir em `prayer_requests` com `name: finalName`, `request: validated.data.request`, `is_anonymous: validated.data.is_anonymous`, `status: 'pending'`, `displayed: false` (PRAY-01).
   - Retornar resposta acolhedora de sucesso ou erro claro em caso de falha de conexão.
</action>

2. Criar `tests/e2e/prayer-security.spec.ts` com testes cobrindo:
   - `hashIp`: gera string hexadecimal SHA-256 consistente com salt, e hashes diferentes para IPs distintos.

   - `prayerFormSchema`: rejeita pedido vazio, rejeita pedido menor que 5 caracteres, rejeita pedido maior que 1000 caracteres, rejeita pedido sem nome quando não anônimo, e aceita pedido sem nome quando anônimo (atendendo aos probes de boundary, empty e encoding PRAY-04).
