<objective>
Implementar o painel completo de moderação pastoral de pedidos de oração (`/admin/oracao`) com fluxo vertical de Server Actions autenticadas (aprovar, rejeitar, desfazer), ordenação FIFO da fila, guias de visualização por status, feedback imediato por Toasts e testes automatizados.

Purpose: Prover à liderança pastoral uma ferramenta ágil, acessível e segura para revisar, aprovar, rejeitar e desfazer moderações de pedidos de oração da congregação antes de sua exibição pública.
Output: Schema de validação `lib/validations/moderation.ts`, Server Actions `app/actions/moderation.ts`, sistema de notificações `components/ui/Toast.tsx`, componente client `app/admin/oracao/ModerationDashboard.tsx`, página `app/admin/oracao/page.tsx` conectada com FIFO e suíte de testes `tests/e2e/prayer-moderation.spec.ts`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Admin UI (Client) → Server Actions | IDs de pedidos enviados por formulários ou botões cruzam a fronteira HTTP para o servidor |
| Server Action → Supabase Database | Atualizações no banco de dados usam credenciais autenticadas respeitando políticas de RLS |
| Usuário Não Autenticado → `/admin/oracao` | Visitantes sem sessão ativa são interceptados e impedidos de ver dados ou disparar moderações |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-01 | Elevation of Privilege | app/actions/moderation.ts | critical | mitigate | Validar estritamente a sessão de usuário com `supabase.auth.getUser()` antes de executar updates em `prayer_requests` |
| T-11-02 | Tampering | app/actions/moderation.ts | high | mitigate | Validação de schema Zod (`moderationActionSchema`) exigindo formato UUID v4 no ID, impedindo payload malicioso |
| T-11-03 | Information Disclosure | app/admin/oracao/page.tsx | high | mitigate | Redirecionamento imediato para `/login` quando `getUser()` não retornar usuário válido, garantindo sigilo pastoral dos pedidos |
| T-11-04 | Repudiation | app/actions/moderation.ts | medium | mitigate | Respostas padronizadas com retorno booleano `success`, mensagens explicativas e tratamento de erros do Supabase |
| T-11-05 | Denial of Service | app/admin/oracao/ModerationDashboard.tsx | medium | mitigate | Utilização de `useTransition` nos botões de ação para prevenir cliques duplicados e disparos concorrentes |
</threat_model>

<action>
1. Criar `lib/validations/moderation.ts` definindo:
   - Schema Zod `moderationActionSchema` com campo `id` validado como UUID (`z.string().uuid({ message: "ID de pedido inválido." })`).
   - Schema Zod `moderationStatusSchema` com status permitidos: `z.enum(['pending', 'approved', 'rejected'])`.
   - Exportação de tipos TypeScript derivados `ModerationActionInput` e `ModerationStatus`.
2. Criar `app/actions/moderation.ts` com a diretiva `"use server"`:
   - Exportar interface `ModerationActionState` contendo `success: boolean`, `message: string`, `error?: string`.
   - Implementar função auxiliar `getAuthenticatedAdminClient()` que obtém cliente via `createClient()` de `@/utils/supabase/server` e valida `const { data: { user } } = await supabase.auth.getUser()`. Se o usuário não existir, lança erro de autorização ou retorna erro de permissão.
   - Implementar `approvePrayerRequest(id: string)`:
     - Valida `id` com `moderationActionSchema.safeParse({ id })`.
     - Verifica autenticação pastoral.
     - Executa update no Supabase na tabela `prayer_requests` definindo `status = 'approved'` onde `id = id`.
     - Executa `revalidatePath("/admin/oracao")` para sincronização imediata do cache da fila (conforme D-04 e MOD-04).
     - Retorna `{ success: true, message: "Pedido aprovado com sucesso!" }` (atendendo MOD-02).
   - Implementar `rejectPrayerRequest(id: string)`:
     - Valida `id` com `moderationActionSchema.safeParse({ id })`.
     - Verifica autenticação pastoral.
     - Executa update no Supabase definindo `status = 'rejected'` onde `id = id`.
     - Executa `revalidatePath("/admin/oracao")` (conforme D-04 e MOD-04).
     - Retorna `{ success: true, message: "Pedido rejeitado com sucesso." }` (atendendo MOD-02).
   - Implementar `undoModeration(id: string)`:
     - Valida `id` e autenticação pastoral.
     - Executa update no Supabase definindo `status = 'pending'` onde `id = id` (atendendo MOD-03).
     - Executa `revalidatePath("/admin/oracao")` (conforme D-04 e MOD-04).
     - Retorna `{ success: true, message: "Moderação desfeita. Pedido retornado à fila de pendentes." }`.
3. Atualizar `app/admin/oracao/page.tsx`:
   - Conectar às Server Actions importadas de `@/app/actions/moderation`, substituindo funções inline do protótipo anterior.
   - Garantir que a verificação de autenticação de sessão e busca no Supabase continuam íntegras (MOD-01).
</action>
